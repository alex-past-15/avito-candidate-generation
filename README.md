# Кандидатогенерация для поиска услуг Авито

Для каждого запроса из `benchmark_queries.parquet` решение выбирает до 50 объявлений
из `benchmark_items.parquet`. Сначала несколько способов поиска собирают общий список
(в среднем около 900 кандидатов на запрос), потом CatBoost оставляет из него лучшие 50.

## Файлы

- `solution.py` - обработка текста, лексический поиск, признаки из train и география.
- `dense.py` - дообучение модели E5 и расчет векторов для объявлений и запросов.
- `split.py` - контрольная выборка для локальной проверки.
- `pipeline.py` - основной скрипт: признаки, обучение CatBoost, `answer.csv`.
- `download_model.py` - один раз скачивает веса E5.
- `selector.cbm` - обученный CatBoost, `validation_metrics.json` - метрики на контроле.
- `models/e5-small-avito` - дообученная модель E5.

## Данные и признаки

Из `train.parquet` беру пары "запрос - выбранное объявление". Они нужны для трех вещей:
найти похожие запросы и посмотреть, что по ним выбирали; дообучить E5; обучить CatBoost.

| Данные | Признаки | Зачем |
|---|---|---|
| текст запроса, заголовок, описание, параметры объявления | BM25 по каждому полю, TF-IDF по кусочкам слов в заголовке, доля слов запроса в поле, есть ли запрос целиком в заголовке | главный сигнал: пользователь ищет словами из объявления. Кусочки слов ловят разные формы слова и опечатки |
| похожие запросы из train и их выбранные объявления | какие микрокатегории и объявления выбирали, слова из заголовков выбранных объявлений | 62% запросов бенчмарка нет в train, но почти всегда есть похожие. Помогает с синонимами |
| текст запроса и объявления целиком | близость по смыслу от дообученного E5 | находит подходящие объявления, даже когда слова совсем разные |
| `search_location_id`, локация и координаты объявления | тот же город, расстояние, как часто из этого города выбирали исполнителей из того города, насколько запрос "локальный" | 83% выборов в train - исполнитель из того же города. Но для онлайн-услуг город не важен, поэтому это признак, а не фильтр |
| `search_infm_params_text` | совпадение фильтров с параметрами объявления | фильтр "Вид услуги" уточняет, что именно ищут |
| `search_category`, категория и микрокатегория объявления | совпадение категории, вероятность микрокатегории | отличает, например, дизайн интерьера от дизайна в Figma |
| рейтинг, отзывы, цена, скрытый телефон, запрет сообщений | как есть | при прочих равных выбирают объявления получше |
| сколько раз объявление выбирали в train | популярность | часто выбираемые объявления выбирают и дальше |

Не использую `search_is_delivery_search` (в бенчмарке он всегда 0) и `query_id`.

## Модели и алгоритмы

1. **Лексический поиск.** Нижний регистр, слова до основы (Snowball, PyStemmer),
   BM25 по словам и парам слов для каждого поля, TF-IDF по кусочкам слов для заголовка.
2. **Поиск по похожим запросам.** Для запроса находим 40 ближайших запросов train
   (по кусочкам слов и по словам) и переносим с них выбранные объявления и микрокатегории.
3. **E5.** Модель `intfloat/multilingual-e5-small` дообучена на парах "запрос и фильтры ->
   заголовок, параметры и начало описания" из train. Функция потерь InfoNCE:
   модель учится ставить выбранное объявление выше остальных объявлений из батча.
   Ее же используем, чтобы найти похожие по смыслу запросы train.
4. **Сбор кандидатов.** Берем топы каждого способа, с учетом географии и без нее,
   и объединяем. В среднем около 900 кандидатов на запрос.
5. **CatBoost** (Logloss, 35 признаков) оценивает каждого кандидата, в ответ идут 50 лучших.

## Как проверял

Первая попытка локально давала 0.90, а на проверке получилось 0.847. В той проверке
нужные объявления добавлялись в корпус извне, и рядом с ними не было похожих объявлений
из того же города. А в настоящем корпусе на каждый запрос приходится около 75 объявлений
из той же локации, так что задача сложнее.

Новая проверка (`split.py`):
- контрольные запросы берутся только из тех записей train, где все выбранные объявления
  уже есть в `benchmark_items`, и ищем ровно по `benchmark_items`;
- доли как в бенчмарке: около 60% запросов с текстом, которого нет в train, около 38% с фильтрами;
- эти запросы полностью убраны из данных, на которых строится поиск и учится E5.

Всего 4 808 контрольных запросов: 3 846 для обучения CatBoost и 962 для оценки.

| Вариант | Recall@50 | Новые тексты |
|---|---|---|
| простая сумма оценок с ручными весами | 0.843 | 0.824 |
| первая попытка (на проверке 0.847) | 0.914 | 0.893 |
| + больше кандидатов, поиск "по всем категориям" | 0.927 | 0.912 |
| **+ дообученный E5 (итог)** | **0.949** | **0.943** |

Локальные числа все равно выше, чем на проверке (у первой попытки 0.914 против 0.847),
поэтому смотрел в первую очередь на прирост относительно первой попытки.

## Ошибки и что с ними сделал

Где теряется качество в итоговом решении: 1.6 пункта - нужного объявления нет даже
среди ~900 кандидатов, 3.5 пункта - оно есть среди кандидатов, но CatBoost не взял его в топ-50.

- **Разные слова для одной услуги.** "Изготовление памятников" и "производство памятников".
  Добавил слова из объявлений, выбранных по похожим запросам, а потом E5, который
  сравнивает смысл, а не слова.
- **Те же слова, но другая услуга.** По запросу "дизайнер фигма" наверх попадали дизайнеры
  интерьера. Помогают микрокатегории похожих запросов и признак "какая доля слов запроса есть в объявлении".
- **Исполнители из другого города.** Онлайн-репетиторы и подобные. Расстояние учитывается
  как признак, а не как фильтр, и часть кандидатов берется совсем без учета города.
- **Новые тексты запросов.** Их находили хуже (0.912 против 0.950 у знакомых). После E5
  разрыв сократился: 0.943 против 0.958.
- **Объявления, которые никто не выбирал в train.** Первая попытка находила их хуже (0.91 против 0.97),
  потому что сильно опиралась на историю выборов. E5 и признаки по тексту от истории не зависят.
- **Размытые запросы**, вроде "база" или "ключ пожарный", где все кандидаты слабые.
  Для них recall около 0.76. Здесь почти нечего улучшить без знаний о пользователе.
- **Поиск по всем категориям.** `search_category = 0` - это 9% бенчмарка, а в train
  таких запросов почти нет. У них ни одно объявление не совпадало по категории, и CatBoost видел
  значения, которых не было при обучении. Теперь для них категория считается совпавшей.
- **Слишком оптимистичная проверка.** Описано выше, отсюда новая `split.py`.

## Запуск

Нужны Python 3.12 и около 16 ГБ RAM. Видеокарта с CUDA желательна, но без нее тоже
работает, только E5 считается дольше. Parquet-файлы задания нужно положить в папку `data`.

```bash
git clone https://github.com/alex-past-15/avito-candidate-generation.git
cd avito-candidate-generation
git lfs pull
```

Для GPU torch ставится с сайта PyTorch:
`python -m pip install torch==2.6.0 --index-url https://download.pytorch.org/whl/cu124`.

```bash
python -m pip install -r requirements.txt
python download_model.py
python split.py
python dense.py --stage train
python pipeline.py --stage index
python pipeline.py --stage control
python pipeline.py --stage bench
python pipeline.py --stage fit
```

По шагам: скачивание весов E5 (нужен интернет, дальше он не нужен), контрольная выборка,
дообучение E5 (около 45 минут на GTX 1660 SUPER) и расчет векторов, индексы, признаки
для контроля и бенчмарка, обучение CatBoost и запись `answer.csv`.
Промежуточные файлы сохраняются в `cache`. Seed везде `20260928`.

Дообученная модель уже лежит в `models/e5-small-avito` (через Git LFS, нужен `git lfs pull`).
Чтобы не учить ее заново, вместо `python dense.py --stage train` можно запустить
`python dense.py --stage encode`: тогда считаются только векторы, это около 7 минут.
Данные задания в репозиторий не входят, их нужно положить в папку `data`.
Формат `answer.csv` проверяется автоматически в конце.

На GTX 1660 SUPER режим fp16 работал примерно в 5 раз медленнее fp32, поэтому E5
учится и считает векторы в fp32. Эмбеддинги словаря заморожены, чтобы хватило 6 ГБ видеопамяти.

## Что использовал

NumPy, pandas, PyArrow, SciPy, scikit-learn, PyStemmer, CatBoost, joblib, threadpoolctl,
PyTorch, Hugging Face Transformers и открытую модель `intfloat/multilingual-e5-small` (MIT).
Внешние API не используются, `query_id` в признаки не входит, разметка бенчмарка нигде не используется.
